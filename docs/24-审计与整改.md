## 0. 三十秒版

**结论**：叙事设计 8/10，机制数值 4/10，原型工程 5/10，文档—代码一致性 4/10。仓库现在是"很好的设计稿 + 一个能走时间的壳"，不是可玩的游戏。**最危险的不是缺功能，而是文档里几处照做会得到错误游戏的硬矛盾**（轴符号、K 链时点、指令点、结局判定）。

**先做的 5 件事**（对应 §3/§4 的多个 P0 条目，不是只有 5 条）
1. **冻结数值基线**：107.9 / 93.7 / +14.2 / 储备 300 / 编制 84 / 士气 61 / 容量 28-48。全仓只留一套。
2. **冻结轴约定**：冷酷 = K+，并补足轴 token，否则 ±40/±60 全部不可达。
3. **重排 K 链时间轴**：门槛只按时钟、征兆窗口移出 S0、S4 只在未收束时存在。
4. **补部门升级与指令点/项目经济**：这是策略层地基，目前 0 定义。
5. **建单一状态层**：`state.js` + 存档 v2 + 回合结束统一结算；现在 5 个状态源 + DOM 当数据库。

**不做什么**：不新增玩法、不美术扩产、不写 SCP 条目。这一轮只做"可计算、可保存、可回归"。

### 0.3 修改纪律（硬性）

1. **先改 §2，再改实现**。任何文档/代码与 §2 冲突，以 §2 为准；发现 §2 本身有问题，先提给 lead，不要自行绕开。

约定：

- **只存可变状态**。站点容量、部门需求线、预算、MTF 隶属是静态表，放 `data.js`，不进存档。
- **派生值不存**：`capacity` 由 `org.sites` 求和；`morale` 顶层由部门均值求；`chain.stage` 由 `clock` 求。
- **冷却单位是回合**（`cooldownTurn`），不是天。
- 所有导入的 JSON 必须先过 `validateSave()`（字段、类型、范围、版本迁移），再进状态层。
- `version` 只增；`migrate(save)` 必须能从 v1 升到 v2。

### 2.4 时间与回合

**回合制是唯一游戏时间**：

- 54 回合；1 回合 = 1 个自然月；`turn` 1..54。
- 所有计时（冷却、排期、门槛、结算）都用 `turn`，不用 `day`。
- `nextTurn()` 是唯一的推进原语：执行"回合结束 → 结算 → 回合开始"，发 `turn:end` / `turn:start`。
- 日期只用于显示：`date = 2026-11 + (turn - 1) 个月`，界面显示 `YYYY·MM`；需要"日"时统一用每月 1 日。开局日 2026-11-20 只作为"任期起点"文案，不参与任何计算。
- 原型的 0/1/2/4× 实时钟**降级为演示模式**（`?speed=` 定时调用 `nextTurn()`），不参与任何结算。
- 09 §4.1 的"没有速度控制——回合制"恢复为设计意图；13 改为"演示时钟"说明。

### 2.5 轴与符号

- **冻结：K+ = 冷酷，K− = 慈爱**。理由：02 §2 表、05 的 K token 绝大多数按"K+ = 冷酷"书写、以及"账本"的语义都已经是这个方向；只改 02 §3/§7/§8 的文字。
- 阈值：±40 生效，±60 锁定。**但必须先补 token**（见 G1）：目标每轴 ≥90 绝对值、≥8 张卡；V 轴至少 10 个 token，P 轴至少 6 个（第 27 回合后）。
- 派系坐标必须数值化：

| 派系 | C | L | K | V | P |
|---|---|---|---|---|---|
| 铁腕 | +1 | +1 | +1 | 0 | 0 |
| 改革 | −1 | −1 | −1 | 0 | 0 |
| 学究 | 0 | 0 | 0 | +1 | +1 |
| 布道 | 0 | 0 | −1 | −1 | +1 |
| O5-1 | 随最近事件移动（每 3 回合更新） | | | | |

忠诚漂移：每回合 `dot(faction, axes) > 0` → +1，`< 0` → −1，`= 0` → 0；P 轴在第 27 回合前按 0 计。

### 2.6 结局状态机

**每条链只有一个终态**：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `hidden` | 未发现 | 初始；S1 前 |
| `omen` | 征兆期 | clock ≤ 85 或首次征兆 |
| `filed` | 已立案 | 花 1 CP + 10 经费 |
| `resolved` | 收束 | 两道门槛都过 + 关键项目完成（clock 归零前） |
| `suppressed` | 镇压 | 花费资源/账本强行终止 |
| `completed` | 失败 | clock = 0（S4） |

**S4 只在未 `resolved`/`suppressed` 时存在**。第二道门槛通过且项目完成 → 立即 `resolved`，时钟停止；否则继续走到 0。这样修掉"S4 落在第 57 回合"的问题。

**结局判定（按优先级从高到低）**：

| 优先级 | 结局 | 条件 |
|---|---|---|
| 1 | 修订 | CK-09 `completed` |
| 2 | 空位 | DBK `completed` |
| 3 | 静默 | ΩK-01 `completed` |
| 4 | 玻璃穹顶 | Lifted Veil `resolved` 且走"公开"分支 |
| 5 | 升维 | awakening = 100 |
| 6 | 共谋 | P ≥ 60 且 ≥3 个异常盟友 |
| 7 | 必要之恶 | K ≥ 60 且 ≥1 条链 `suppressed` |
| 8 | 传承 | turn 54 且无 `completed`（觉醒 < 50 时用主文案；50–99 用变体文案；这是兜底结局） |

**评分公式（替换 01 §8）**：

```
score = turn
      + 2 × veil
      + 20 × archiveIntegrity        // 1 - 改写条数 / 总条数
      + 10 × resolvedChains
      − 3 × ledger
```

删除"未完成 K 链数"（在"活到 54 且无 completed"下恒为常数）；账本只作为结局分支/叙事反馈，不再进分数（否则它就是 02 明令禁止的善恶值）。若 lead 坚持保留账本项，必须同时删掉 [02:86](02-意识形态.md#L86) 的"它不改变数值"承诺。

### 2.7 数据流与模块边界

```
data.js (静态表：需求线/预算/站点/MTF/政府/卡库)
    ↓
state.js (create / reduce / subscribe / serialize / migrate)
    ↓            ↑
engine.js (纯函数：turn, deck, chain, resolve)     ← 不碰 DOM
    ↓
render/*.js (只读 state；textContent 写 DOM；不改 state)
    ↓
store (localStorage) + export/import JSON (validator)
```

- 面板不再各自读 `SAVE_DEFAULT`；一律从 `state` 取。
- `GameAPI` 只暴露 `getState / dispatch / subscribe / nextTurn / save / load`。
- `ui.js` 只做热区与视觉反馈，不写业务状态。

## 3. 游戏设计缺陷与修改要求

> 每条：**症状 → 证据 → 要求 → 验收 → owner**。P0 必须先做，P1 其次。

### G1（P0）轴系统与卡库的 token 预算对不上

**症状**：02 的所有效果挂在 ±40/±60，但 05 全库只有 37 个轴 token；按每卡一次的上限，C+27 / L+33 / K+32、K−51 / V−15 / P+30。**没有一根轴能到 +40**（K− 的 51 是唯一越过 ±40 的，方向是慈爱）；**没有任何轴能到 ±60**；V 轴全库只有一个 token。

**证据**：[02:19](02-意识形态.md#L19)、[02:40](02-意识形态.md#L40)、[02:124](02-意识形态.md#L124)；05 选项行统计；[05:236](05-事件卡库.md#L236)。

**要求**：
- 02 冻结 K+ = 冷酷；改 §3 K 轴行、§7 四个原型、§8 结局 2 的符号。
- 05 补 token：每轴 ≥8 张卡、≥90 绝对值；V 轴 ≥10 个 token；P 轴 ≥6 个（第 27 回合后可见）。
- 每张卡标注 `axisOnce`（关键卡 true；日常卡可重复，但重复只计半值，防刷）。
- 新增校验：`tools/content-check.mjs --axis` 用"专注单轴"模拟跑 1000 局，报告每轴到 +40 的概率；要求 ≥70%。

**验收**：模拟报告达标；02/05 符号一致；无"阈值为 40 但最大 33"的轴。

**owner**：content + lead

### G2（P0）部门成长机制不存在

**症状**：01 说每部门 0–5 级、每级一个能力/暗面；21 算"70 个能力节点"；实际只写了 14 行，**没有任何升级成本/条件/耗时**。而 03 的核心论断"一条链需要主部门 3 级、8–12 回合堆到"建立在这上面。

**证据**：[01:168](01-设计总纲.md#L168)、[21:158](21-部门取舍.md#L158)、[03:277](03-K级情景链.md#L277)。

**要求**：
- 新增"部门升级表"：每级 `经费 + CP + 回合 + 前置部门等级/项目`，并写明升级动作发生在回合的哪个阶段。
- 先写**每部门 3 级**（不是 5 级）的必需能力：14 × 3 = 42 个节点；4–5 级进 backlog。
- 升级必须与项目共享同一套 CP 经济（见 G3），不能是免费点击。
- 21 的"70 个节点"改成"42 个 v1 节点 + 28 个 backlog"。

**验收**：给出一条"从第 1 回合开始专注一个部门，第 12 回合到 3 级"的可执行时间表（含每回合 CP/经费支出），并能被 econ/engine 模拟复现。

**owner**：lead + economy
